# Decisions Log — Project 1: Text-to-SQL with Clarification Engine

Pattern for every: **What / Why / Trade-off**

---

## D1: PostgreSQL 16 via Docker Compose (not local install, not Supabase)
- **What:** Postgres 16 runs in a Docker container defined in `docker-compose.yml`.
- **Why:**
  - Reproducible - anyone clones the repo, runs `docker compose up -d`, gets the
    identical environment. No "works on my machine."
  - `seed.sql` auto-loads on first startup by mounting it to `/docker-entrypoint-initdb.d/`.
  - Zero cost, fully local, data never leaves the laptop.
- **Trade-off:** Supabase (hosted Postgres) is available and may be used later for
  a deployed demo, but local Docker is faster for dev iteration and free.

## D2: Named volume `pgdata` for database persistence
- **What:** Postgres data directory is mounted to a named volume `pgdata`.
- **Why:** Containers are disposable - deleting the container would destroy data
  written inside it. The volume survives container deletion.
- **Trade-off:** `docker compose down` (no `-v`) keeps data; `down -v` wipes it.
  We deliberately use `-v` during development to force a fresh seed load,
  because init scripts only run when the data directory is empty.

## D3: Seed file is fully generated by script (schema + data in one file)
- **What:** `scripts/generate_data.py` writes the ENTIRE `data/seed.sql`:
  DROPs, CREATEs, INSERTs, and sequence resets. Write mode `"w"`, never `"a"`.
- **Why:** One command = one complete reproducible database. Append mode would
  duplicate data on re-runs.
- **Trade-off:** None worth noting — regeneration takes <1 second.

## D4: CHECK constraints on status and payment method
- **What:** `orders.status` limited to ('delivered','shipped','cancelled','pending');
  `payments.method` limited to ('card','cash','online','wallet').
- **Why:** Databases are the last line of defense against bad data. App-level
  validation can have bugs; constraints cannot be bypassed by a forgetful dev.
- **Trade-off:** Changing allowed values requires a migration - acceptable at
  this scale, and it forces us to keep the Python generator and schema in sync
  (single source of truth principle).

## D5: Explicit IDs in seed inserts + setval sequence resets
- **What:** Seed INSERTs specify explicit primary keys; three `setval(...)` calls
  at the end reset each SERIAL sequence to MAX(id).
- **Why:** Explicit IDs let us maintain referential integrity (orders know their
  customer). But SERIAL sequences don't advance on explicit-ID inserts - without
  setval, the first app-level INSERT would fail with a duplicate key error.
- **Trade-off:** Slightly longer seed file vs. avoiding a classic production bug.

## D6: Realistic messy data (cancelled orders, unpaid orders, clamped dates)
- **What:** ~65% delivered / 15% shipped / 10% cancelled / 10% pending; some valid
  orders left unpaid; payment dates clamped so nothing is in the future;
  signups backdated ≥30 days so "last month" queries are meaningful.
- **Why:** Real company data is messy. Queries like "best customer" behave
  differently on messy data - which is exactly the ambiguity our clarification
  engine will target. We control the data, so we know the ground truth →
  evaluation becomes possible.
- **Trade-off:** More complex generator script, but it doubles as evaluation setup.

## D7: venv + .gitignore hygiene (.env never committed)
- **What:** All Python deps in a local `venv/`; `.gitignore` excludes `venv/`,
  `__pycache__/`, `.env`. Notes and decisions.md are COMMITTED (portfolio evidence).
- **Why:** Secrets in git are a real security incident (leaked API keys get scraped
  within minutes). `.env.example` with dummy values shows collaborators which
  variables to set.
- **Trade-off:** None. This is non-negotiable practice.

## D8: Schema tables — customers, orders, payments
- **What:** 3 tables. customers(customer_id, name, email, city, signup_date),
  orders(order_id, customer_id FK, order_date, status),
  payments(payment_id, order_id FK, amount, payment_date, method).
- **Why:** Minimal but rich enough to produce ambiguous questions:
  "best customer" = most orders? most revenue? most repeat visits? All three
  are answerable with different queries - that ambiguity IS the project.
- **Trade-off:** No products/inventory table - kept scope minimal for clarity.
